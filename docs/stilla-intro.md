# Stilla：一个把「确定性」当信仰的小语言

> 面向陌生读者的语言介绍：特性、设计取舍，以及与 C++、Rust、Go、Elixir，以及嵌入式脚本方案 Lua、QuickJS 的对照。
> 本文基于 Stilla 的三份规范（Core / Runtime / Standard Library，均为 v1.3 Draft）编写。

---

## 1. 一句话定位

**Stilla 是一个小型的、静态类型的语言**，为四类用途设计（Core §1.1）：

- **嵌入式脚本**（embedded scripting）——嵌进宿主程序里跑的脚本语言；
- **确定性执行**（deterministic execution）——同样的输入，每次运行的结果、资源释放的顺序都完全一致；
- **宿主集成**（host integration）——与 C/C++ 之类的宿主程序深度协作；
- **机器生成代码**（machine-generated code）——作为代码生成器（包括 LLM）的输出目标，语法应当小到生成器不会出错。

支撑这四点的是一条总原则：**语言的模型必须从源码里直接看得见**。没有隐藏的 GC 线程、没有偷偷运行的构造器、没有编译器悄悄帮你改变求值顺序。你读到的代码，就是机器要做的事。

## 2. 设计原则：五组核心立场

Core §1.2 把设计原则归纳为五组，理解了它们就理解了整门语言：

1. **不可变与确定性**——绑定（binding）一律不可变；正常控制流上的析构顺序确定；子表达式严格从左到右求值；没有可变全局状态。
2. **值是一等公民，状态不是**——代数数据类型（struct / union）是普通的值；文件就是模块，模块就是值；没有隐式接收者；没有继承。
3. **所有权显式、按值传递**——显式 `borrow`（借用）与 `move`（移交）；**没有追踪式垃圾回收**。
4. **函数单态、无捕获**——表达式导向的控制流；一等函数值，但**不能捕获闭包**；泛型在编译期展开。
5. **模块按值组织、静态解析**——模块里只有模块级绑定；`import` 静态解析。

再加上五条「中心规则」（Core §1.3），其中两条最能体现性格：

> **终止规则**：正常控制流确定性析构；panic 直接终止、**不展开（unwinding）**，清理交给宿主。

## 3. 三十秒示例：斐波那契

```stilla
const builtin = import("builtin");

fn fib(n: int32) -> int32 {
    if (n < 2) { n } else { fib(n - 1) + fib(n - 2) }
}

fn main() -> void {
    builtin.print(builtin.str(fib(10)));
}
```

（示例片段。）

注意这里没有 `return` 语句、没有循环、没有隐式的 `print`。函数体是一个表达式，最后一个表达式的值就是返回值；重复执行靠**递归**；所有名字都通过 `import` 显式引入。这些都不是偶然的省略，而是设计决定——下面逐条展开。

## 4. 核心特性

### 4.1 文件即模块，模块即值

每个 `.st` 源文件就是一个**隐式的、不可变的模块结构体**（Core §2）。模块成员就是模块结构体的字段：

```stilla
const calc = import("calc");

fn main() -> void {
    builtin.print(builtin.str(calc.add(20, 22)));
}
```

`calc.add` 是**普通的值成员访问**，不是静态函数查找——模块与 struct 共用同一套 `.` 成员模型。`import("...")` 只能出现在模块级 `const` 的初始化式里，解析必须静态确定，禁止循环导入（Core §2.4），每个模块在同一执行上下文内至多实例化一次（Runtime §2.1）。

模块级 `const` 按声明顺序初始化，且不允许（传递地）引用声明在后面的常量——保证模块常量只会在初始化完成后被读取（Core §5）。

### 4.2 不可变绑定

本地绑定用 `let`，全部不可变：

```stilla
let x = 10;
let y = x + 20;
// x = 30;  ← 编译错误
```

允许遮蔽（shadowing）：

```stilla
let x = 10;
let x = x + 1;   // 右侧 x 指旧绑定
```

源码因此天然是 SSA 友好的（Core §4）。没有可变状态，是「易推理」的第一块基石。

### 4.3 表达式导向：没有 `return`，也没有循环

`if`、`match`、代码块都是表达式（Core §13）：

```stilla
let sign = if (value >= 0) { 1 } else { -1 };
```

条件必须加括号（消解控制流体与 struct 构造之间的歧义）；`if` 无 `else` 时整个表达式类型必须是 `void`。

**核心语言没有循环构造**（Core §13.5）。重复用递归表达；标准库的 `iter` 模块提供 `fold` / `each` 等组合子（见 §4.7）。有趣的是，编译器的优化器会把尾递归改写回循环——源码里没有循环，机器码里可以有。

### 4.4 代数数据类型与模式匹配

数据用**结构体**（struct）和**带标签联合**（union）表达，没有继承、没有方法语法（Core §7、§11）：

```stilla
union Shape {
    circle(int32), rect(int32, int32)
}

fn area(s: Shape) -> int32 {
    match (s) {
        Shape::circle(r) => r * r * 3,
        Shape::rect(w, h) => w * h,
    }
}
```

（示例片段。）

`match` 必须穷尽所有变体；模式支持字面量、元组、struct、union 变体、列表形状（`[head, ..tail]`）等（Core §13.3）。`let` 只接受不可反驳（irrefutable）的模式——绑定永远不会引入隐式的运行时失败路径（Core §14）。

递归类型必须通过间接（`box[T]`、`list[T]` 或函数类型）打破存储循环（Core §11.3）。

### 4.5 所有权：没有 GC，但有纪律

这是 Stilla 与「托管语言」最根本的分水岭。所有值分两类（Core §10）：

- **Copy**——可隐式复制，析构无操作。如 `int32`、`float32`、`bool`、`str`、函数值。
- **unique（唯一值）**——不能隐式复制；至多被移交一次，必须恰好被析构一次（可以被多次借用）。任何定义了 `drop` 钩子的 struct、或含有 unique 成分的复合值都是 unique。

对 unique 值有三种显式操作：

```stilla
fn show(borrow t: Token) -> int32 {   // 借用：只读视图，不转移所有权
    t.id
}

fn consume(move t: Token) -> void {   // 移交：所有权进入函数
    drop t;                           // 显式析构
}
```

（对应示例程序。）

- `borrow` 参数是**非拥有的只读视图**，调用者仍是所有者，可以借多少次都行；
- `move` 参数接收所有权，把已存在的唯一值传给它必须写 `move a`（Core §10.6）；
- 所有权转移只作用于**完整的局部绑定**（whole-owner rule）——不支持字段、下标的部分移动（Core §10.4）。想拆出成分，用解构（destructuring）：`let Pair{ first, second } = move pair;`。

编译器静态检查全部规则：用了已移动的值是编译错误；在条件分支的某些路径上释放了绑定，它会变成 **maybe-unique**——之后不可用，作用域结束时的析构由运行时存活标志守护（Core §10.10）。

这一切换来的是**没有 GC**：没有暂停、没有后台回收线程、资源释放的时间点完全可预测。

### 4.6 确定性析构与 `drop` 钩子

一个 struct 可以声明**至多一个**析构钩子（Core §9）：

```stilla
struct File {
    fd: int32;
    path: str;

    drop(file) {
        os.close(file.fd);
    }
}
```

正常控制流上，析构顺序完全确定（Runtime §6）：

1. 用户 `drop` 钩子先跑；
2. 唯一字段按**声明顺序的逆序**析构；
3. 值标记为已析构。

局部变量在作用域结束时按**创建顺序的逆序**自动析构。钩子内看到的是「析构视图」：能读字段、能借用，但不能移动、不能逃逸（Core §9.2）。显式 `drop` 语句可以在中途提前析构一个唯一绑定，之后该绑定不可再用。

需要说明的重要区别：Stilla 的 struct **不是**「类」——没有构造器（struct 字面量 + 普通工厂函数即可，Core §8）、没有私有性控制（v1.3 明确不做，Core §8.3）。

### 4.7 没有闭包，以及它的补偿机制

Stilla 的函数和 lambda **不能捕获外围局部绑定**（Core §6.2）。这直接杀死了「闭包」这个表达力之源，换来的是：函数值的表示极其简单（单态、非捕获的代码引用），没有堆分配的闭包环境，机器生成代码时不用考虑捕获分析。

语言为此提供了两条补偿路径：

1. **函数值字段**——struct 里可以存函数值，配合显式接收者（没有 `receiver.method()` 糖，Core §6.1）；
2. **上下文线程化（context threading）**——`iter` 模块的 `*_with` 组合子额外接受一个被借用的上下文，每次调用都传给操作函数：

```stilla
let sum = iter.fold[int32, int32](builtin.range(1, 10), 0,
    fn(move acc: int32, borrow x: int32) -> int32 { acc + x });
```

（`builtin.range` 是闭区间。）

`iter` 提供 `each` / `fold` / `try_fold`（短路折叠）及其 `*_with` 和 `consume_*` 变体（StdLib §7）。`try_fold` 用 `Result[S, R]` 表达提前停止——这也顺带给出了标准库的 `Result` 类型。

### 4.8 泛型 = 编译期单态化

泛型是**编译期的模板展开**，运行时没有任何泛型函数值（Core §12）：

```stilla
fn identity[T](move value: T) -> T {
    move value
}

let x = identity::[int32](42);   // 显式特化
let y = identity(7);             // 参数可推断 T 时省略
```

`identity::[int32]` 是编译期特化语法，不是运行时后缀运算。`let f = identity;`（未特化的泛型）是编译错误；`let f = identity::[int32];` 才是合法的单态函数值。没有 trait、没有约束、没有泛型函数类型（`fn[T](T) -> T` 不存在）——换来实现和推理的极简。

代价是每个特化都生成一份代码（代码膨胀），以及少了一整层抽象能力。

### 4.9 求值顺序与陷阱：确定性是硬承诺

全语言只有**一条求值顺序规则**（Runtime §5）：

> 除非构造显式另说，子表达式在源码顺序中恰好从左到右求值一次。

覆盖调用（先 callee 后实参）、成员/下标、二元操作数、tuple/list/struct 字面量、match 先求 scrutinee 等一切场景；`and` / `or` 短路。这不是「优化提示」，规范明确禁止在可观察行为上做手脚。

运行时的失败都是**确定性的陷阱（trap）**（Runtime §7.2）：整数溢出、除零、越界索引、非法数值转换、非法的 `any` 恢复——全都 trap，没有未定义行为。浮点遵循 IEEE 754 binary32（注意：Stilla 只有 `float32`，没有 `f64`）。

### 4.10 panic：终止，不展开

`builtin.panic` 或任何运行时陷阱会**终止整个执行上下文**（Runtime §7.1），并且：

- 不展开栈，不恢复执行；
- **不执行任何待执行的析构**（局部变量、临时值、模块 teardown 都不跑）；
- 控制立即交还嵌入宿主，由宿主负责清理。

这与 C++/Rust 的「异常/panic 展开栈并运行析构函数」是刻意相反的路线：Stilla 认为清理责任应属于宿主（它看得见整个上下文），而不是语言运行时。代价是语言内**没有恢复机制**——没有 `try`/`catch`/`recover`。错误处理靠 `Option`/`Result` 值 + `builtin.assert` + 终止式 panic 三件套。

### 4.11 嵌入边界：`any` 与 `hostdata`

宿主集成是设计目标，语言为此准备了两个「边界类型」（Core §11.6、§11.7）：

- **`any`**——顶部类型（top type），任何类型的值都可以放进 `any`。它携带**运行时类型标签**，恢复必须显式命名类型：`a as int32`（标签不匹配则 trap），或 `match` 的类型测试模式（`int32 n => ...`，对 `any` 的 match 必须有 `_` 通配臂，因为标签空间是开放的）。`any` 本身是 unique（它可能装着唯一值）。
- **`hostdata`**——**不透明的宿主负载**。只有宿主能构造，Stilla 无法检查、无法转换、无法比较它，只能移动、借用、存储、原样递给宿主。`array[T]` 和 `hashmap[K, V]` 就构建在它之上。

标准库的集合因此很特别（StdLib §2、§3）：`array` 是宿主实现的连续内存缓冲；`hashmap` 的 `insert` / `remove` 是**持久式（persistent）**的——消费旧 map、返回新 map，从不原地部分修改：

```stilla
let m0 = hm.empty::[int32, str]();
let m1 = hm.insert::[int32, str](m0, 1, "one");
let m2 = hm.insert::[int32, str](m1, 2, "two");
```

（示例片段。）因为是 `hostdata` 负载，容器**永远是 unique**，即使元素类型是 Copy——所有权整体转移，绝无部分突变。

### 4.12 标准库

`builtin`（print、str、len、range、box/peek/unbox、panic、assert、hash）、`math`（IEEE 754 float32 函数）、`string`（按 Unicode 码点操作，永不暴露字节偏移）、`iter`（列表组合子）、`array`、`hashmap`。全部是**普通可导入的模块**——没有隐式注入的 `print()`，`str` 的字符串拼接只允许 `str + str`，没有隐式数值转换（Core §16）。语言核心刻意保持很小：只有 `list[T]` 是抽象内建类型，`array`/`hashmap` 是库类型，想替换它们不需要改语言。

## 5. 设计取舍总览

| 领域 | Stilla 的选择 | 常见语言的典型选择 | 收益 / 代价 |
| --- | --- | --- | --- |
| 内存管理 | 无 GC，显式所有权（borrow/move/drop） | GC（Go、Elixir）或完整借用检查（Rust） | 收益：确定性、无暂停；代价：程序员负责资源纪律 |
| 析构 | 确定性析构 + `drop` 钩子；panic 不展开、不析构 | 异常展开跑析构（C++/Rust）；GC 无析构 | 收益：生命周期可预测；代价：panic 后靠宿主清理 |
| 可变性 | 全部不可变 | Rust 局部 `mut`；C++/Go 默认可变 | 收益：易推理、SSA 友好；代价：必须函数式风格 |
| 循环 | 无；递归 + `iter` 组合子 | `for`/`while` 普遍存在 | 收益：语言更小；代价：新手要适应递归 |
| 闭包 | 无；函数值 + 上下文线程化 | 各语言普遍支持 | 收益：函数表示极简、无捕获分析；代价：表达力显著受限 |
| 泛型 | 编译期单态化，无约束 | C++ 模板、Rust trait、Go 约束、Elixir 动态 | 收益：零运行时开销、实现简单；代价：代码膨胀、无抽象层 |
| 动态派发 | 无；`any` + 运行时标签，恢复必须显式 | Go `interface`、C++ 虚函数 | 收益：静态可分析、确定性；代价：类型恢复啰嗦且会 trap |
| 错误处理 | 终止式 panic + `Option`/`Result` | C++ 异常、Rust `?`、Go error、Elixir let-it-crash | 收益：路径少；代价：无恢复、错误即终止 |
| 继承 / 方法 | 无；ADT + 普通函数 + 显式接收者 | C++ 类、Go 方法、Rust trait | 收益：无隐藏机制；代价：样板代码偏多 |
| 模块 | 文件 = 不可变模块值 | Go package、C++ 头/源二元、Elixir module | 收益：模块即数据、成员访问统一；代价：模块值不能进本地数据流 |
| 求值顺序 | 单一从左到右规则 | C++ 众多构造未限定 | 收益：完全可预测 |
| 嵌入宿主 | 一等设计：`hostdata`、宿主模块、宿主可调用任意模块函数（Runtime §3.3） | Lua / QuickJS C API、Go cgo | 收益：嵌入边界干净；代价：宿主需要实现接口 |
| 数值 | `byte`/`int32`/`uint32`/`float32` | 各语言类型更全 | 收益：实现面小；代价：数值表达力有限 |

## 6. 与六门语言的对照

### 6.1 对比 C++：确定性是保证，不是纪律

**共同点**：值语义、确定性析构（C++ 的 RAII ↔ Stilla 的 `drop` 钩子与作用域析构）、没有 GC、对资源生命周期有完全控制、都能贴近硬件层。

**关键差异**：

- **求值顺序**：C++ 在众多构造中求值顺序未被限定（C++17 后部分场景已规范，但远非全部），未定义行为（UB）让「确定性」只能是编程纪律；Stilla 用一条硬规则消灭了这个维度。
- **异常与析构**：C++ 异常**展开栈并运行析构函数**（RAII 的基石）；Stilla 的 panic **明确不展开、不运行任何析构**。这是最有趣的一处分歧——两者都承诺「资源会被释放」，但 C++ 说「即使出错也要释放」，Stilla 说「出错时释放交给宿主，语言不掺和」。
- **机制面**：类、继承、多态、运算符重载、模板元编程、宏、头文件/源文件二元性——Stilla 全部没有。`drop` 钩子 ≈ 析构函数，但只能有一个、不能被直接调用、panic 时不执行。

**一句话**：C++ 给你全部控制权，也把全部责任给你；Stilla 砍掉大部分机制，把「析构一定发生、顺序确定」变成语言保证。

### 6.2 对比 Rust：所有权模型的最小公倍数

**共同点**：所有权/借用/移动、无 GC、内存安全不靠运行时、ADT + 模式匹配、编译期单态化泛型、确定性析构（Rust 在作用域退出和 panic 展开时都会析构）。Stilla 的 `borrow`/`move`/`drop` 三件套一眼就是 Rust 的简化形态。

**关键差异**：

- **借用系统的规模**：Rust 有生命周期参数、可返回引用、引用可存储、`Send`/`Sync` 并发保证；Stilla 的借用**只限于词法可见的范围**——`borrow` 参数和 `builtin.peek` 的瞬态借用，**不能**返回借用值，**没有**生命周期参数（Core §10.7）。代价是表达力（比如不能写返回引用的函数），收益是整个借用检查可以词法判定、实现面小一个数量级。
- **可变性**：Rust 默认不可变但允许 `mut` 局部；Stilla 全部不可变，没有 `mut`。
- **panic**：Rust 默认 unwind 并运行析构；Stilla 终止、不运行任何析构。
- **表达力层**：Rust 有 trait、方法语法、闭包、迭代器链；Stilla 没有 trait、没有方法糖、没有闭包。
- **数值与并发**：Rust 类型系统丰富、可安全并发；Stilla 只有 4 种数值类型，核心无并发概念（v1.3）。

**一句话**：Stilla ≈ 把 Rust 的借用系统裁到「词法即可判定、无需生命周期参数」的最小规模。适合需要确定性资源管理、但不需要 Rust 全部表达力的场景。

### 6.3 对比 Go：两种「简单」，不同的来源

**共同点**：把「小」当作设计目标、易嵌入、无继承、编译为原生代码、快速启动、面向系统编程。

**关键差异**：

- **确定性的来源**：Go 用 GC + 运行时换简单（defer 的释放依赖程序员纪律）；Stilla 用显式所有权换确定性（释放是语言保证）。两条路径都有效，但「何时释放」在 Go 里不可预测，在 Stilla 里是编译期已知的。
- **并发**：Go 的杀手锏是 goroutine/channel；Stilla 核心语言没有并发（v1.3 明确不在范围内）——它把并发留给宿主。
- **动态派发**：Go 有 `interface` + 反射；Stilla 用 `any` + 运行时标签，但恢复必须显式命名类型且失败即 trap，没有隐式动态派发。
- **错误处理**：Go 有 `panic`/`recover`（可捕获）；Stilla 的 panic 终止上下文，**没有 recover**。Go 的错误值惯例在 Stilla 里的对应物是 `Option`/`Result`。
- **嵌入方式**：Go 嵌入靠 c-shared 等较重绑定；Stilla 从设计第一日起就是宿主语言——`hostdata`、宿主模块、宿主可调用任意模块函数（Runtime §3.3）。

**一句话**：两者都追求简单，但 Go 的简单来自运行时兜底，Stilla 的简单来自把责任显式化并静态检查。

### 6.4 对比 Elixir：函数式内核与「崩溃即交接」

**共同点**（这组对照最有趣）：

- **不可变数据**：Elixir 的一切都不可变、持久化数据结构；Stilla 绑定不可变、`hashmap` 持久式更新。
- **函数式风格**：表达导向、模式匹配、**递归优于显式循环**。Stilla 的 `iter.fold` 与 Elixir 的 `Enum.fold` 是同一个思想；`[head, ..tail]` 列表模式与 Elixir 的 `[head | tail]` 同源。
- **容错哲学**：Elixir 的「let it crash」——进程崩溃不清理、交给 supervisor 重启；Stilla 的「panic 终止上下文、不展开、宿主接管清理」。两者都拒绝「展开栈并尽力清理」的模型，把崩溃后的处置权交给外层。

**关键差异**：

- **类型系统**：Elixir 动态类型；Stilla 静态类型 + 显式所有权 + 确定性析构。
- **并发**：BEAM 进程、消息传递、每进程 GC 是 Elixir 的根基；Stilla 无并发。
- **闭包**：Elixir 的 `fn ... end` 可以捕获（有闭包）；Stilla 没有闭包，用 `*_with` 上下文线程化补偿。
- **元编程**：Elixir 的宏是强项；Stilla 没有任何宏。
- **资源管理**：Elixir 靠进程终止时 BEAM 回收资源；Stilla 靠编译期所有权保证释放，且**知道确切时机**。

**一句话**：两者共享函数式内核与「崩溃即交接」的容错观，但 Elixir 把确定性和容错交给 BEAM 运行时，Stilla 把确定性交给编译器和显式所有权——一个靠运行时兜底，一个靠静态保证。

### 6.5 对比 Lua：嵌入式脚本的行业标准

Lua（PUC-Rio，1993 年）是嵌入式脚本领域的事实标准：小、快、C API 成熟，从游戏（魔兽世界、Roblox）到 Redis 脚本、OpenResty 都在用它。作为同生态位的后来者，Stilla 与 Lua 的对照是最直接的。

**共同点**：

- **为嵌入而生**——单一 C API、每次一个独立的解释器状态（Lua 的 `lua_State` ↔ Stilla 的执行上下文）、宿主通过注册函数/模块向脚本暴露能力；
- **轻量**——Lua 的实现只有约 3 万行 C、运行时仅几十 KB 量级；Stilla 的设计目标同样是「小到能嵌进任何地方」；
- **函数是一等公民**——两者都靠函数值组织行为。

**关键差异**：

- **类型系统**：Lua 动态类型，`table` 是万能结构（数组、记录、对象一表通吃）；Stilla 静态类型 + ADT。Lua 的灵活靠运行时解释，Stilla 的保证靠编译期检查。
- **内存管理**：Lua 用增量标记-清扫 GC（5.4 还提供分代模式），回收时机由内存压力决定、不可预测；Stilla 显式所有权 + 确定性析构，释放时机编译期即知。这是两者最根本的分歧。
- **可变性**：Lua 的变量**默认是全局的**（要局部必须写 `local`），一切可改，元表还能改写语义；Stilla 全部不可变、无元编程。
- **错误处理**：Lua 用 `error()` + `pcall`/`xpcall`（保护调用：错误被捕获为状态码返回，控制回到 `pcall`——期间不会有任何清理代码执行，因为 Lua 根本没有析构概念）；Stilla 的 panic 同样不展开，但区别在于 Stilla **有**确定性析构，只是刻意让 panic 路径跳过它、把清理交给宿主。
- **表达力**：Lua 有闭包、协程、多重赋值；Stilla 无闭包、无协程、无多重赋值——它是用表达力换可分析性。
- **性能**：LuaJIT 的 JIT 让 Lua 逼近 C 的速度；Stilla 单态化 + 无 GC，内存行为编译期可预测，但并没有（也不承诺）JIT。

**一句话**：Lua 用「最小化的动态语义 + 成熟的 C API」统治嵌入脚本三十年；Stilla 的定位是「同样轻，但把确定性从运行时搬到编译期」——用静态类型与所有权，换可预测的释放时机和可静态分析的脚本。

### 6.6 对比 QuickJS：把完整 JavaScript 装进 200KB

QuickJS（Fabrice Bellard，2018 年）是另一个嵌入方案：一个几乎完整支持 ES2025 的 JavaScript 引擎，却只需几个 C 文件、无外部依赖，hello world 的 x86 代码约 210 KiB，整个运行时实例的生命周期不到 300 微秒。

**共同点**：

- **同为嵌入设计**——C API、宿主对象、独立上下文（`JSContext`/`JSValue` ↔ 执行上下文/`hostdata`）；
- **提前编译的思维**——QuickJS 的 `qjsc` 可以把 JS 编译成 C 源码/字节码甚至无依赖的可执行文件，与 Stilla「编译期单态化、面向机器生成代码」的气质一致：尽量把工作放到编译期。

**关键差异**：

- **语义面规模**：QuickJS 的目标是兼容完整的 ECMAScript——类、async/await、生成器、BigInt、模块、Proxy、正则……语言面巨大；Stilla 刻意选择最小语义面。
- **内存管理**：QuickJS 用**引用计数 + 周期回收**（官方明确说引用计数「为了确定性的行为」），无环对象随引用消失而立即释放，但环需要周期扫描、时机依赖内存压力；Stilla 的价值语义 + 不可变绑定从源头排除了「可变环」——共享只能发生在不可变值上（`str` 和 Copy 容器允许引用计数共享），因此连周期回收都不需要。
- **清理机制**：JS 的资源释放要么靠 GC（时机不定），要么靠程序员手写 `try/finally`；Stilla 的 `drop` 是编译器管理的确定性清理。JS 的 `finally` 保证「代码一定会执行」，Stilla 保证「析构一定会发生且顺序确定」——一个靠纪律，一个靠语言。
- **错误处理**：JS 异常会展开栈并执行 `finally`；Stilla 的 panic 不展开、不执行任何析构。
- **类型与确定性**：JS 动态类型、闭包是核心表达手段；Stilla 静态类型、无闭包。JS 的不确定性来自 GC 时机与宿主环境（时钟、随机数、I/O）；Stilla 的核心语义完全确定。

**一句话**：QuickJS 证明了「完整的 JS 也能塞进 200KB」；Stilla 选了相反的路线——用更小的语义面 + 静态所有权换取语言级的确定性，而不是引擎级的尽力而为。

## 7. 适合什么，不适合什么

**适合**：

- **嵌入宿主的脚本层**——游戏引擎、设备固件、配置/规则引擎，需要宿主语言（C/C++/Rust）与脚本之间干净的边界（`hostdata`、宿主模块）。这一生态位目前由 Lua 与 QuickJS 主导，Stilla 是带着不同承诺的竞争者：释放时机确定、行为可静态分析；
- **对确定性有硬要求的系统**——资源生命周期必须可预测、不能有 GC 暂停、执行顺序必须可复现（例如测试、回放、审计敏感的场景）；
- **机器生成代码的目标**——语法小、无歧义（括号强制）、单一求值规则、无宏无闭包，生成器很难写出「能编译但行为诡异」的程序；
- **教学**——所有权、ADT、函数式核心在极小的语言里一览无余。

**不适合**：

- **大型应用开发**——没有闭包、trait、动态派发、并发，表达力不足以支撑大项目；
- **重数值计算**——只有 `float32`/`int32`，没有 `f64`/向量类型；
- **需要恢复机制的领域**——错误即终止的 panic 模型不适合需要优雅降级的服务端场景；
- **需要丰富生态或插件架构的场景**——没有动态派发和反射式的扩展点。

## 8. 现状

Stilla 目前是 **v1.3 Draft**。语法、特性与编译器均不稳定，正在持续演进，暂时不支持上手体验。本文的代码示例与当前草案保持一致，但会随草案修订而变化。

---

**一句话总结**：Stilla 是「Rust 的所有权 × 函数式语言的不可变核心 × 嵌入式宿主的集成哲学」，再用「确定性」把三者焊在一起——它刻意放弃表达力，换来一个从源码完全可见、行为完全可预测的小语言。
